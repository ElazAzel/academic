# OWASP Top 10:2025 — локальная копия чеклиста

Источник: https://owasp.org/Top10/2025/ (релиз 2025, категории A01–A10).
Зеркало официального списка + рабочий чеклист для ревью кодовой базы
проекта «AI Strategic Academy» (Next.js 16 App Router + Prisma/PostgreSQL +
Auth.js + shadcn/ui). Используется скиллом `owasp-top10-2025` и субагентом
`security-guard`.

## Список категорий (2025)

1. **A01:2025 — Broken Access Control** (нарушенный контроль доступа)
2. **A02:2025 — Security Misconfiguration** (небезопасная конфигурация)
3. **A03:2025 — Software Supply Chain Failures** (сбои цепочки поставок)
4. **A04:2025 — Cryptographic Failures** (криптографические недостатки)
5. **A05:2025 — Injection** (инъекции)
6. **A06:2025 — Insecure Design** (небезопасный дизайн)
7. **A07:2025 — Authentication Failures** (неудачи аутентификации)
8. **A08:2025 — Software or Data Integrity Failures** (нарушения целостности ПО/данных)
9. **A09:2025 — Security Logging and Alerting Failures** (недостатки логирования/алертинга)
10. **A10:2025 — Mishandling of Exceptional Conditions** (неправильная обработка исключений)

## Чеклист для стека Next.js + Prisma/Postgres

### A01 Broken Access Control
- Каждое API-действие и server action явно проверяет права текущего пользователя
  (`requirePermission`/`requireRolePage`); не доверять ID из запроса; не полагаться
  на скрытие UI.
- RLS включён на всех таблицах Postgres; политики покрывают select/insert/update/delete
  отдельно.
- Идентификаторы записей в URL недоступны чужому пользователю (IDOR).
- Серверные роуты и actions повторяют авторизацию; клиентские проверки — только UX.

### A02 Security Misconfiguration
- Никаких дефолтных кредов и debug-режимов в проде.
- Заголовки: CSP (nonce-based), X-Content-Type-Options, frame-ancestors; cookies с
  HttpOnly/Secure/SameSite.
- Публичные бакеты/таблицы перечислены осознанно; `service_role` ключ только на
  сервере, никогда в браузере или бандле.

### A03 Software Supply Chain Failures
- Зависимости минимальны; перед добавлением — проверка maintained/популярности.
- Lockfile коммитится; обновления через `npm audit`, без слепых мажорных апгрейдов.
- Не выполнять скрипты из непроверенных источников; CI использует pinned action-версии.

### A04 Cryptographic Failures
- Секреты только в env (сервер); никакого хардкода токенов/ключей; не логировать их.
- Пароли — только через встроенный провайдер (argon2id внутри Auth.js), не свои хеши.
- Чувствительные данные по HTTPS; токены в localStorage — осознанное решение с учётом XSS.

### A05 Injection
- Работа с БД только через Prisma (параметризованные запросы); конкатенация SQL из
  пользовательского ввода запрещена (в т.ч. в `.rpc()` и raw-фильтрах).
- React экранирует вывод автоматически — опасность: `dangerouslySetInnerHTML`,
  `href`/`url` из данных (`javascript:`), markdown-рендер без санитайзации.
- Валидировать типы/форматы входных данных на сервере (Zod), не доверять клиенту.

### A06 Insecure Design
- Думать о злоумышленнике до кода: что можно абузить в фиче.
- Лимиты и квоты на мутирующих операциях (создание записей, импорт, отправка сообщений).
- Флоу восстановления доступа, приглашения и шеринга проектировать как границы доверия.

### A07 Authentication Failures
- Сессии истекают; logout инвалидирует; после смены пароля — переавторизация.
- Единая точка проверки auth (middleware `proxy.ts` + layout), не разрозненные проверки.
- Коды подтверждения (Telegram link-code) — одноразовые, с коротким TTL.

### A08 Software or Data Integrity Failures
- Данные из внешних источников (webhook, импорт CSV) валидировать по схеме до записи.
- Webhook-эндпоинты проверяют подпись/секрет отправителя.
- Автообновления и внешние скрипты — только из доверенных источников с фиксацией версий.

### A09 Security Logging and Alerting Failures
- Значимые события логируются: отказы доступа, неудачные входы, смена привилегий,
  подозрительная активность.
- В логи не попадают персональные данные и секреты.
- Ошибки пользователю понятны, но не раскрывают внутренности (стеки, SQL, пути).

### A10 Mishandling of Exceptional Conditions
- Ошибки обрабатываются явно: никаких пустых catch и «падаем молча».
- Fail securely: при сбое — запрет по умолчанию, а не открытый доступ.
- Пользователь получает безопасное сообщение; детали уходят в серверный лог/error boundary.

## Быстрые проверки для этого проекта
1. `grep` по проекту: `service_role`, `SUPABASE_SERVICE`, `dangerouslySetInnerHTML`,
   `NEXT_PUBLIC_.*KEY` — секретные значения не в публичном бандле.
2. Все `app/api/**` роуты: есть ли проверка сессии/прав до обращения к данным.
3. Все таблицы: `rls_enabled = true`; политики не вида `USING (true)` для приватных данных.
4. Пользовательский ввод в SQL/raw/rpc — только параметризованно.
5. Зависимости: `npm audit` перед релизом; новые пакеты — обосновать в PR.

Правило: найденные проблемы нельзя замалчивать — исправить или явно вывести в ответ со
ссылкой на категорию (A01–A10) и планом исправления.
